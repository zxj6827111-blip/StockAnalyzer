## 2. 产品行为与数据契约

### 2.1 正式晚报的唯一来源

正式晚报只能来自**一次明确完成的夜扫结果**，保存后冻结。

不得在发送或补发时重新读取可能已被进化复扫、盘中雷达更新的通用 `latest`、`watchlist` 或共享候选状态来拼接报告。

报告分为四种结果：

| `scan_status` | 用户看到的结论 | 处理要求 |
|---|---|---|
| `completed` | 今日选股完成，有隔夜观察候选 | 展示真实候选 |
| `empty` | 今日正常完成，无合格候选 | 展示主要过滤原因 |
| `blocked` | 数据或必要检查未通过，未完成有效选股 | 明确阻断原因 |
| `failed` | 扫描异常或超时 | 明确失败阶段 |

“数据失败没有选出来”不得解释成“今天没有机会”。

旧池回退使用独立字段记录，必须标明原交易日，不计入今日入选数量。

### 2.2 候选口径

- 观察候选沿用夜扫现有 `night_pool` 规则和排序。
- 正文最多展示 5 只；只有 1 只就展示 1 只，不补足数量。
- 全部候选保存在报告中。
- 评分、理由和风险从当轮结果取值，不在渲染时重新评分。
- 股票名称缺失时展示代码及“名称暂缺”，不得因名称查询失败阻断整个报告。
- 夜间结果始终标注为“隔夜观察”，不生成买入指令。
- 风险评估输入不足的条目单独列为“数据待补全”，不混入通过完整检查的候选。

保留最终筛选数量作为审计字段，但不能把它表述为已经通过次日实时确认的买入信号。

### 2.3 消息内容

正式消息标题：

`【晚间选股报告】YYYY-MM-DD`

正文必须包含：

1. 扫描结果和候选数量。
2. 实际数据日期。
3. 前 5 只候选的代码、名称、分数、入选依据、主要风险。
4. 筛选漏斗数量。
5. 无候选或失败时的原因。
6. “隔夜观察，盘中条件需另行确认”的说明。

正文控制在约 3,000 个中文字符以内。按固定顺序截断过长理由，保留日期、状态、股票和关键风险；完整内容保存到报告。第一版使用现有文本消息，不引入卡片系统。

### 2.4 现有消息兼容

- 白天消息保留。
- 正式晚报不依赖进化任务成功。
- 进化消息中的“候选股票：入围 N 只”改为“进化复扫中间短名单 N 只，非正式晚间观察池”。
- 进化消息引用正式报告时，必须绑定明确的 `report_id`，不能另取实时观察池冒充。
- 第一版不关闭进化任务，也不改变它的参数控制逻辑。

### 2.5 冻结报告与状态存储

使用现有 artifacts 命名卷，新增：

```text
runtime/nightly_reports/<trade_date>/<report_id>.json
runtime/nightly_reports/<trade_date>/state.json
runtime/nightly_delivery/<delivery_id>.json
```

职责：

- 报告文件：不可变的业务结果。
- 日期状态：夜扫阶段、运行身份、已发布报告指针、重试次数。
- 交付文件：该报告对具体目标的发送状态。

报告最小字段：

```text
schema_version
report_id
trade_date
generated_at
run_id / trace_id
code_commit
config_hash
data_snapshot_id
scan_status
data_gate
funnel_counts
observation_candidates
incomplete_candidates
final_selection_count
exclusion_summary
fallback_source_date
```

所有时间使用带时区的 ISO 8601，业务日期按 `Asia/Shanghai` 和项目交易日历计算。

采用现有文件锁和原子替换。报告写入成功后才能发布指针、建立待发记录；恢复任务必须能修复“报告已保存、待发记录尚未建立”这一中断状态。

不得扫描整个历史目录恢复；仅检查当前交易日及最近一个交易日的日期状态和待发记录。

## 3. 可靠交付、接口与调度实现

### 3.1 职责划分

新增两个窄职责服务：

- `NightlyReportService`：报告构造、冻结存储、版本、消息渲染。
- `NightlyDeliveryService`：待发记录、目标结果、并发控制、重试、恢复。

现有夜扫服务负责调用它们；大型运行服务只增加接线和调度入口，不继续承载完整实现。

### 3.2 交付状态

每个接收目标独立保存：

```text
pending
sending
retry_wait
delivered
unknown
exhausted
```

定义：

- `delivered`：目标飞书 API 明确接受。
- `unknown`：请求可能已被接受，但本地无法确认，例如请求超时或发送后进程退出。
- `exhausted`：明确失败且重试预算耗尽。
- `console` 输出不能产生 `delivered`。

飞书接受与用户实际阅读是不同事实。部署验收需要用户收件确认，运行系统不伪造“已读”。

### 3.3 复用通道与兼容性

沿用既有主应用目标与企业分发配置，不新建机器人、不修改收件人。

- 主应用目标为必需目标。
- 企业分发沿用当前可选目标语义。
- 必需目标成功后，正式报告可判交付成功。
- 可选目标失败保留告警和独立状态，不重发已成功的主目标。
- 不根据 `feishu_app+feishu_enterprise` 字符串推断两路都成功。

为新晚报提供明确的逐目标交付接口，复用现有凭据获取和传输逻辑。旧 `send()` 及其返回字段保持兼容，不全局改变白天通知的成功语义。

新接口返回：

```text
target_key
outcome: accepted | failed | unknown
message_id（接口返回时）
error_code
error_message（脱敏）
accepted_at
```

HTTP 200 不能单独算成功；响应必须可解析，且明确业务成功。缺失业务状态的异常响应不得默认成功。

### 3.4 幂等和重试

- 同一报告、同一目标对应稳定 `delivery_id`。
- UUID、正文及内容摘要在首次尝试前保存，重试不得变化。
- 已成功的目标不再发送。
- 同一交易日正式报告内容确需更新时产生新版本，标题标注“修订版”。
- 普通重启、补发不得产生新报告版本。
- 不使用现有“发送前写去重缓存”的 `_notify_if_changed` 作为晚报交付依据。

主应用发送接入稳定请求 `uuid`。飞书官方 SDK 文档说明，相同 UUID 在一小时内至多成功执行一次；它只能补充本地持久化去重，不能替代长期交付记录。[飞书官方 SDK 文档](https://larksuite.github.io/oapi-sdk-java/com/lark/oapi/service/im/v1/model/CreateMessageReqBody.Builder.html)

重试规则固定为：

- 首次失败后：1、5、15 分钟退避。
- 首次加 3 次重试，总共最多 4 次。
- 通过调度时间实现，不在 worker 内长时间 sleep。
- 网络超时等不确定结果，在首次尝试后 50 分钟以内使用同一 UUID 重试。
- 超过此窗口仍不确定，停止自动重发并保留 `unknown`，交由人工核对，避免跨去重窗口重复推送。
- 可选渠道没有已核实的幂等能力时，不自动重试不确定结果。
- 明确认证、目标不存在、权限错误不进行高频重试，记录为需处理状态。

### 3.5 并发和崩溃恢复

使用专用交付锁，不占用候选状态锁进行网络请求。

- 同一 `delivery_id` 的锁覆盖状态读取、发送和回执写入。
- 单次网络调用总预算最多 20 秒。
- 锁持有者进程消失后，遗留 `sending` 按不确定结果恢复，不当作从未发送。
- 持有者仍存活但请求缓慢时，其他 worker 不得接管并重复发送。
- 发送响应成功但回执落盘失败，必须保留可恢复证据，不吞掉异常。

### 3.6 查询与补发接口

保持现有夜扫 API 的旧字段兼容。

扩展已有鉴权 `GET /week5/night-scan/latest`，增加：

```text
report_id
trade_date
scan_status
delivery_status
required_target_delivered
last_delivery_error
```

新增鉴权接口：

`POST /week5/night-scan/reports/{report_id}/retry-delivery`

规则：

- 只操作已存在的报告，不重新扫描。
- 只补发未成功目标。
- 已全部成功返回幂等无操作结果。
- 不允许传任意文件路径或任意接收人。
- `unknown` 且超出去重窗口时返回冲突状态，需要显式确认可能重复才可人工补发。
- 接口仅入队，不阻塞等待网络结果。
- 查询接口不得返回凭据或完整接收人身份。

### 3.7 夜扫调度与时间预算

新增晚报功能开关；关闭时保留旧调度行为。

启用时：

- 夜扫仍从交易日 21:45 开始。
- 使用每 5 分钟一次的检查入口，最晚 23:00 启动一次新的重型扫描。
- 先检查该交易日是否已有有效完成记录，再检查数据 readiness。
- 数据未就绪快速返回 `waiting_data`，不在重型 worker 中等待 900 秒。
- 实际扫描仍保留 1,800 秒预算，不扩大其他 Week5 任务超时。
- 同一交易日重型扫描最多执行 2 次；数据等待检查不计入执行次数。
- 成功完成或正常空结果后，后续触发只做幂等返回。
- 失败重试不得与仍在运行的扫描并发。

夜扫是否已完成，使用夜扫自身的交易日、数据版本和完成状态判断；不能继续依赖会被盘中任务改写的共享 `state.trade_date/data_version`。

### 3.8 交付检查与告警

新增 `nightly_delivery_tick`，放入现有 critical 组：

- 每分钟检查一次。
- 每次最多处理 2 个到期交付目标。
- 独立任务超时 120 秒。
- 不执行选股、不更新行情、不等待重型扫描。
- 日期报告、待发记录和调度状态是其输入。

固定行为：

- 22:30 尚未完成：最多发送一次“延迟说明”。
- 23:30 尚未形成有效结果：最多发送一次明确失败或阻断摘要。
- 扫描完成但交付失败：报告状态仍保留完成，交付状态另列。
- 延迟、失败、正式结果分别使用不同消息类型和去重键。
- 延迟提醒发出后，晚到的正式结果仍可发送。
- 主机或网络整体故障时保留状态，恢复后如实补报，不承诺离线期间飞书一定能报警。

静默窗口沿用 `00:30—08:30`。明确未发送的结果可在窗口结束后补发并标原日期；不确定发送不得因此跨过幂等窗口盲目补发。

### 3.9 readiness 消费兼容

进化任务可能消费并重命名 readiness 文件。

- 已冻结报告补发不再依赖 readiness 文件。
- 开扫前保存当次 readiness 证据。
- 新扫描只能使用符合当前交易日、版本及数据检查的就绪证据。
- 不无条件接受历史 `consumed` 文件。
- 本轮不全局重写 readiness 消费协议；缺乏有效证据时明确阻断，并按截止规则报告。

## 4. 过热缺输入修复与测试要求

### 4.1 修复规则

保留 PR #82 的统一指标计算和现有风险阈值。

新增 `evaluation_status`：

- `evaluated`：输入有效，完成风险判断。
- `insufficient_input`：历史或指标不足。

保留现有 `level` 枚举兼容，但缺输入时不得只依赖 `level=none` 判断安全。

要求：

- 缺输入指标使用 `null` 或缺键。
- 禁止回退到 `ma5=1.0`、`atr14=0.03` 参与真实判定。
- 最终买入准入显式拦截未完成必要风险评估的结果，原因是“输入不足”，不是“过热”。
- 正式观察报告单列数据待补全条目。
- 调用方缺少新字段时，新鲜生产结果必须补齐状态；历史旧报告只能作为旧版本解释，不能默认已经完整评估。
- 检查 evaluator 全部调用方，确保生产与历史评估使用同一输入语义。

### 4.2 必须通过的测试矩阵

| 类别 | 场景 |
|---|---|
| 报告内容 | 1 只、5 只、超过 5 只、正常 0 只 |
| 异常语义 | 数据阻断、扫描异常、超时、旧池回退 |
| 来源一致 | 进化短名单不同、盘中更新后补发、名称缺失 |
| 交付判定 | 飞书成功、业务错误、无效响应、console 成功 |
| 多目标 | 主目标成功/可选失败、主失败/可选成功 |
| 幂等 | 重复触发、重复补发、报告修订、稳定 UUID |
| 恢复 | 重启、报告写入后崩溃、发送后回执写入前崩溃 |
| 并发 | 两个 worker 竞争、持锁慢请求、持有者退出 |
| 重试 | 明确失败、不确定结果、超出去重窗口、预算耗尽 |
| 调度 | 数据晚到、漏跑、进程终止、heavy 被占满 |
| 日期 | 周末、节假日、跨日、静默窗口、原日期补发 |
| readiness | 缺失、旧日期、其他任务已消费 |
| 风险 | 足量正常行情、真实过热、仅 3 根行情、无效数值、无有效 ATR |

测试必须使用隔离状态目录和 fake notifier，不得向真实飞书发送单元测试消息。

除新增测试外，运行现有 Week5、调度器、通知、配置、过热输入相关回归，以及仓库要求的质量检查。先完成针对性测试，再执行一次完整回归；历史失败与本轮引入失败分开报告。

不得只验证 helper，必须覆盖实际生产入口以及最终选择消费结果的路径。

## 5. 执行批次、NAS 上线与交付标准

### 5.1 批次顺序

| 批次 | 内容 | 放行条件 |
|---|---|---|
| A | 固定报告、状态类型、统一消息口径 | 内容与来源测试通过 |
| B | 逐目标交付、持久化、幂等、重试 | 故障与并发测试通过 |
| C | 夜扫调度、等待预算、漏跑检查 | 日期、超时、恢复测试通过 |
| D | 过热缺输入边界 | 生产入口及既有回归通过 |
| E | 集成、部署、真实收件及夜间验收 | 端到端证据完整 |

各批次独立提交，提交说明记录测试命令和结果。未完成 B、C 前不得把 A 单独上线并宣称闭环完成。

### 5.2 zcode 开始前检查

1. 阅读适用的 AGENTS.md 和现有部署说明。
2. 记录本地实际 HEAD、分支和工作区差异，保护现有诊断文档。
3. 只读刷新 NAS 的代码、镜像、挂载、调度配置和有效通知目标。
4. 不输出密码、token、webhook 和完整收件人标识。
5. 建立工作分支 `codex/nightly-selection-delivery`；若已存在，先检查其工作，不覆盖或重置。
6. 所有测试数据使用隔离目录，正式产物不提交 Git。

### 5.3 NAS 部署方式

### 5.5 验收级别

分别报告以下结论：

- **本地代码通过**：目标测试及回归通过。
- **NAS 部署通过**：目标构建、配置和心跳正确。
- **消息交付通过**：既有目标 API 接受且用户确认收到。
- **夜间功能通过**：真实交易日自动完成正常选股或正常空结果并交付。
- **运行稳定**：连续 3 个交易日完成上述自动闭环。

数据失败但故障消息送达，只能判“故障可见”，不能判“选股成功”。

若实施时尚未到夜间，交付必须写“真实夜间验收待完成”，不得用回放结果替代。保留后续验收步骤和待检查交易日，不虚报稳定运行。
