## 0. 结论摘要

方向不是"把校准调好、把模型调优"，而是三步走：**先让度量可信 → 再把模型复杂度砍到与数据量匹配 → 最后把训练池从策略候选池改回全可交易截面**。

在度量可信之前，任何模型改动都无法被验证——这是本次最重要的产出。工作量的分布也反直觉：真正便宜且高价值的是 P0，真正难的是 P1 的池子改造。

| 批次 | 内容 | 目的 | 是否阻塞后续 |
|---|---|---|---|
| **P0** | L1–L7 | 让"模型好不好"这件事变得可测量、可审计 | 阻塞一切模型调优 |
| **P1** | L8–L12 | 让模型复杂度与有效样本量匹配、修训练池 | 决定能否产出可用的模型 |
| **P2** | L13 | 加长历史（最高杠杆的数据投入） | 决定 P1 的上限 |

## 2. 核心约束：有效样本量约 200

这条约束决定了 P1 全部内容，先讲清楚：

- 本次训练 24,018 行、120 个决策日，标签 horizon 10 天 → **互不重叠的时间块约 12 个**。
- 同日约 330 只票的收益高度相关（市场/板块 beta 主导），单日有效独立下注数按 10~30 计。
- 两者相乘，**有效独立观测约 200 量级**。

在这个量级上拟合 222 个特征 + 两个 GBDT + 一个 isotonic 校准器，train in-sample AUC 0.9187 / test 逐日 0.5321 这个落差是必然而非意外。**isotonic 尤其不成立：它需要大量样本估计单调映射，而它只有 2,410 个样本、来自单一 12 天行情窗。**

推论：P1 的方向只能是**降复杂度 + 加历史**，不能是加特征、加模型类别、调超参。

## 3. 整改项

### P0 批次 — 让度量可信

#### L1 登记退化门禁（fail-closed）

- **问题**：一个常数预测器可以正常登记进 registry，`blocked_reason` 为空，`auc_valid=1.0`。`auc_valid` 只检查两类标签都存在，等于没有检查。
- **证据**：F2 + F3。三个互相独立的退化信号（spread 0.000272、校准后取值数 4、`positive_rate` 0.9937）全部进入了 metrics，却没有任何一项被判定为不合格。
- **改法**：在登记前置一道门禁，任一条件触发即拒绝登记并记 `blocked_reason`：
  - `mean_prob_spread < 0.005`（阈值待定，需先用历史工件标定分布）；
  - 校准后预测的唯一取值数 < N（N 待定，建议 20）；
  - `positive_rate` 落在 [0.30, 0.70] 之外；
  - train in-sample 与 OOS 的 AUC 落差 > 0.30。
  阈值必须**先用历史工件回测标定**（现有 18 个工件正好是标定样本），不能拍脑袋，否则会把未来的正常工件挡在门外。
- **验收**：用 9/13 这个工件做回归用例（必须被拒）；用 8/24 工件做对照组（行为待定，见 §6 决策点 3）。
- **成本/风险**：小（1–2 天）。风险是阈值过紧误杀，故先标定后启用，并允许 advisory 模式跑一段时间。

#### L2 工件内 raw / calibrated 指标分离

- **问题**：`metrics_summary_json` 只有一套指标，且是**校准后**的。要判断一次改动是帮了模型还是帮了校准器，只能靠手工加载 sidecar 重算——本次就是这么才发现根因的。
- **证据**：F4 与 F5 的差异（raw 0.5321 vs cal 0.5035）在 registry 里完全不可见。
- **改法**：工件与 registry 同时记录 `auc_raw` / `auc_calibrated` / `mean_prob_spread_raw` / 校准前后 unique 值数；`training_diagnostics` 报告同步。
- **验收**：对同一工件，registry 里的 `auc_raw` 与附录 A 脚本二独立重算结果一致（允许小幅抽样差异，需在文档里写清允差来源）。
- **成本/风险**：小。纯增量字段，不改行为。

#### L3 晋升口径换成 18-fold walk-forward，manifest split 降级为冒烟

- **问题**：当前晋升判断建立在一个 test split 上。该 split 的成熟日跨度只有 12 天 ≈ **1.2 个互不重叠的 10 天周期**，在统计上无法区分 IC 0.05 与 0。
- **证据**：F7（test 成熟日 08-27~09-11，12 个成熟日、3,990 行）+ F9（同一 split 在决策日轴上被报成 23 天）。
- **改法**：
  1. 晋升门 = 18-fold walk-forward IC 的置信区间（沿用现有 harness `backtest/walk_forward_xsec.py`）下界 > 0；
  2. manifest split 的指标只作为"管线没坏"的冒烟检查，不参与晋升；
  3. 报告里必须同时给 CI，不给单点 IC。
- **验收**：用 9/13 工件跑 18-fold，得到 IC 与 CI，与 18-fold 硬门基线（+0.0658）对照。
- **成本/风险**：中（harness 已有，主要是接线与报告口径）。风险是 18-fold 单次成本高，需确认可接受的重跑频率。

#### L4 切分口径与门禁口径统一（**本次结论已纠正**）

> **纠正记录**：我在第一轮口头汇报里说过"embargo=0、没有 embargo"。实测后确认**这句话是错的**：embargo 机制不仅存在，而且在本次 manifest 上真实生效（F7，同一成熟日跨 split = 0）。真正的问题是下面三点。

- **问题 a（审计误导）**：指标把实际生效的 embargo 记成 0（F8）。任何审计者读 `embargo_days=0.0` 都会得出"没有 embargo"的结论——包括我自己。
- **问题 b（口径不一致，后果最实际）**：门禁按**决策日**算跨度、切分按**成熟日**做分组。于是门禁报 23 天通过，而按它自己要用量的那个轴只有 16 天，**低于它自己设的 20 天门槛**（F9）。也就是说这道门当前没有在量它想量的东西；90 天窗被它拦下（决策日轴 9 天）和全窗口被它放行（成熟日轴 16 天），是两个口径混用的结果，不是数据质量的真实差异。
- **问题 c（同一决策日跨段）**：5 个决策日同时落在 calibration 与 test（F10，合计 6 行）。根因是少数行的成熟日比同侪晚一周（同一决策日的成熟日分成两组），分组按成熟日走，边界就从这一天中间穿过去了。数据量上微不足道（0.15%），但它让"样本外"的宣称在**日粒度**上不成立。
- **改法**：
  1. 把切分口径写进 manifest 与指标：记录各段成熟日边界、实际 embargo 天数；`embargo_days` 不再恒为 0；
  2. 门禁的 window_days 改为在**切分所用的轴**（成熟日）上计算，或两轴都报并且以成熟日轴为准判门槛；
  3. 决策日粒度上强制"一个决策日 → 一个 split"（按决策日分组，或对边界日做 purge 并记录）；
  4. 重新标定 `min_test_split_window_days`：若按成熟日轴，当前 20 天的门槛会让本次 manifest 也不合格——这需要你决定是放宽门槛还是接受全窗口也只有 16 天成熟日的现实。
- **验收**：新增断言测试：(i) 任一决策日不跨 split；(ii) 指标的 embargo 与 manifest 实际分组一致；(iii) 门禁的 window_days 与 split_plan 在同一轴上。
- **成本/风险**：小到中。风险在改门槛会改变"什么算合格数据集"的既有判断（见 §6 决策点 2）。

#### L5 champion 身份链修复

- **问题**：registry 里 `role=champion` 记录数为 0（F12），而生产在跑 `/app/artifacts/model_v1.json`（F11）。从 registry 答不出"线上是哪个模型、它的 hash 和口径是什么"。这不是本轮引入的，是 Week5 Phase 0 就已记录的遗留。
- **证据**：F11 + F12；另外 challenger 的 `parent_model_id = champion_v7_202603` 指向一条不存在的记录。
- **改法**：把在服工件反向登记为 champion（含 hash、口径、created_at），或明确把 auto_load 路径改为只认 registry 里的 champion；两者选一，不能继续两头并存。
- **验收**：`select * from model_registry where role='champion'` 非空，且其 `artifact_uri`/hash 与实际被 auto_load 的文件一致。
- **成本/风险**：小。但在改之前必须先冻结线上模型文件，避免登记与实物再次脱钩。

#### L6 选样阶段只物化元数据

- **问题**：协议训练入口一次性把窗口内全部快照物化为 pydantic 对象（F13），导致生产 4 GiB 容器必然 OOM；本次是靠一次性 8g 维护容器绕开的。
- **证据**：F13；`service.py:9265` 的 `list_snapshots` 之后还有 symbol 过滤，即先全量物化再过滤。
- **改法**：两段式——先只取 `(snapshot_id, symbol, decision_time)` 之类元数据完成选样与截断，再按最终 id 集合回取特征；或让 `SampleStore` 提供投影查询。
- **验收**：在 4 GiB 容器内完成全池训练不 OOM；并记录 peak RSS 作为回归基线。
- **成本/风险**：中（要动 SampleStore 的查询接口与调用点）。这是唯一一条"不改就无法在生产容器里正常重训"的工程项。

#### L7 记账补全与同名歧义

- **问题 a**：manifest 记 40,000 行、数据集 24,018 行，而 `rows_dropped_by_dedup=0`、`time_gate_dropped_rows=0`——被标签过滤剔掉的 15,982 行没有任何一处记账（F14）。数字对得上（60.05% ≈ 1−0.4），但读报告的人会以为数据"凭空少了"。
- **问题 b**：`positive_rate` 一词指两件事。`trainer.py:914` 的是 `mean(meta >= 0.5)`（预测正率，模型是常数时必然趋近 1），`config.py:1343-1344` 的 `m5_positive_ratio_low/high`（0.30/0.70）是**标签**正率的均衡门。两者同名，极易误读——我在第一次读指标时就被误导过。
- **改法**：a) 在数据集组装处记录"label 过滤剔除行数"并进 metrics；b) 给两者改一个不会混的名字（如 `predicted_positive_rate` vs `label_positive_ratio`），并在文档与报告里统一。
- **验收**：metrics 里 `included_snapshot_count - dataset_rows = label_filter_dropped_rows` 恒等式成立。
- **成本/风险**：小。

### P1 批次 — 让模型与数据量匹配

#### L8 把概率校准从关键路径上拿掉

- **问题**：标签是横截面分位排序，要的输出是**排名**不是概率；isotonic 是 soup 时代（TP/SL 二分类、阈值有意义）的遗留，在 ~200 有效观测上不可识别。
- **证据**：F3 + F5（校准窗原始 AUC 0.4435 → 校准器塌成常数 → 最终 AUC 0.5035）。
- **改法（三选一）**：
  - **A（推荐）**：v3 路径不做概率校准，直接输出可排序分数；下游改用横截面排名或分位。
  - B：保留校准但换成 2–3 参数的低自由度单调映射（如 logistic on rank），并在长窗上拟合。
  - C：滚动 walk-forward 校准（最正确、最贵，建议留到 P2 之后）。
- **前置动作（必须先做）**：盘查下游到底谁在消费概率——`score_floor`、仓位计算、执行风险门、以及哪些门禁吃概率。若只是二值化决策，A 的改动面很小；若有仓位依赖，选 B。这一步没做完不要动。
- **验收**：改动后 18-fold IC 不劣于当前 raw 分数基线（逐日 AUC 0.5321 / IC +0.0555），且工件不再出现常数。
- **成本/风险**：A 小、B 中、C 大。风险是下游有隐性概率消费者，必须靠前置盘查消除。

#### L9 单模型 + 强正则，或线性基线；去掉无效融合

- **问题**：两个 GBDT 在 ~200 有效观测上的方差远超线性模型；融合权重是 `lgbm 0.500239 / xgb 0.499761`（`trainer.py:870` 的 inverse-Brier），两个 Brier 几乎相同 → 这个环节没有携带任何信息，纯属复杂度。
- **证据**：F5 的 in-sample 0.9187（严重过拟合）；metadata 的 `meta_blend_weights`。
- **改法**：先建一个**线性/ridge 基线**（特征做横截面 rank 标准化），再决定是否值得引入树模型。任何集成必须证明其 OOS 增益覆盖复杂度成本。
- **验收**：线性基线与树模型在同一 18-fold harness 下的 IC/CI 对比表；若树模型无显著优势，采用线性。
- **成本/风险**：小（baseline 本身很快），大的是"接受更简单的模型"这个决策。

#### L10 特征从 222 降到 10~30，且必须在 fold 内筛选

- **问题**：222 个特征中，300 行抽样下只有 137 个有变化；我在诊断中给出的"top-15 复合 IC +0.1046"是**全样本筛选**结果，含选择偏差，不能当基准用（F6 已标注）。
- **改法**：每个 walk-forward fold 内独立做 IC 筛选，只用该 fold 之前的数据；报告 fold 间被选中特征的稳定性（这会直接告诉你信号是否稳定）。
- **验收**：fold 内筛选后的 OOS IC + 特征入选频率表。
- **成本/风险**：中。fold 内筛选会显著增加 harness 运行时间。

#### L11 训练池改为每日全可交易截面（**我认为最深的一条**）

- **问题**：当前池子只有 334 只票（F15），是回填覆盖 + 策略选出的候选子集。在这种子池上计算横截面分位标签，模型学到的是"我已选出的候选里哪个会涨"，而不是"哪些票会涨"。
- **证据**：Phase 1 候选池 IC +0.239 vs Phase 2 全市场 PIT IC −0.024，同口径下差异只能由池子组成解释（前序结论）。
- **改法**：横截面模型在全集（或口径一致、可复现的资格集）上训练；策略候选只用于最终选择，不参与训练池定义。
- **验收**：同一模型在"候选池"与"全市场池"上的 OOS IC 对比，并给出池子覆盖率（当前全市场覆盖约 334/5,191 = 6.4%）。
- **成本/风险**：**大**。要重建 PIT 特征面板、扩快照采集、重做回填；这是 P1 里唯一可能以周计的项。

#### L12 把反转因子显式化，并用单因子基准当靶子

- **问题**：目前最强也最稳定的信号是短期反转——动量族特征一致为负（F6），118 天 t≈−4.5，且在两个池子上复现。而系统在做一个 222 特征的非线性模型去找它。
- **改法**：把反转做成显式因子 + 透明排名组合，作为 benchmark；任何更复杂的模型必须**先打败这个 benchmark**才有存在理由。
- **验收**：单因子反转排名组合的 OOS 表现 vs 现模型；若现模型打不过，直接采用因子方案。
- **成本/风险**：小（一天量级），价值可能最大。

### P2 批次 — 数据

#### L13 加长历史

## 4. 明确不做

1. **不给在服模型翻符号**。AUC 0.3314 看着像"反着用就行"，但树模型对排序标签翻符号不成立；且 soup 标签本身已被诊断为口径错误（`docs/week5_label_remediation_report_20260907.md`），翻符号修不了根因。
2. **不调校准窗口长度/分段点**。那是拟合症状。
3. **不加特征、不加模型类别、不做超参搜索**。有效样本量已把上限定死（§2）。
4. **不在 L1 落地前让任何东西晋升**。
5. **不把 `positive_rate` 当标签平衡度看**（L7-b）。
6. **不通过改受跟踪的 `docker-compose.memlimit.yml` 来跑训练**。本次用一次性 8g 维护容器绕开是正确姿势，长期解法是 L6。

## 附录 A：证据复现方式

所有探测均在 NAS 上以 `docker exec -i <container> python - < 脚本` 执行，只读打开 `learning_protocol.duckdb`（`read_only=True`），**不使用 `docker cp`**。脚本已清理，需要时按下列口径重建：

1. **脚本一（特征 IC）**：SQL 直连 `signal_snapshots × outcome_records`（`label_policy_id='label_policy_v3_b0b3724553b5'`，`decision_time >= '2026-01-16'`，`limit 40000`），逐块解析 `feature_vector_json`（**不要**走 `SampleStore.list_snapshots`，会 OOM），再调用生产函数 `labels.return_rank.apply_return_rank_labels_by_day` 生成标签，逐日算 rank IC。
2. **脚本二（raw vs 校准）**：加载 `artifacts/model_archive/model_v2_e0e264cb3547ca9ec95d/model.json`（注意 sidecar 在**子目录** `model_sidecars/`），用 `lightgbm.Booster` / `xgboost.Booster` 直接打分，再用工件里的 `*_calibrator.x_right/y_hat` 手写 `searchsorted` 映射，分窗对比 AUC/IC。
3. **脚本三（注册表）**：`select * from model_registry order by created_at desc`，分组统计 role × lifecycle_state。
4. **脚本四（切分）**：`dataset_manifest_items × signal_snapshots × outcome_records` 按 `split_name` 聚合，同时看**决策日**与**成熟日**两个轴，并检查同一成熟日/同一决策日是否跨 split。
5. **脚本五（在服工件）**：读 `/app/artifacts/model_v1.json` 的 `metadata` 与 `lgbm_calibrator`。
6. **OOM 判据**：容器 `memory.peak`、`memory.events.oom_kill`，配合 `dmesg`（NAS 上受限）。

## 附录 B：本次诊断过程中的两次自我纠正

写在这里是因为它们直接影响上面几项结论的可信度，也说明为什么 L2/L4-a/L7 值得单列：

1. **"sidecar 文件丢失"** → 错。我用 `os.path.join(base, basename(rel))` 拼路径，漏了 `model_sidecars/` 子目录，误判为文件缺失。重新全局搜索后确认 sidecar 存在且 sha256 齐全（291,862 B / 164,786 B）。**教训：判断"文件不存在"之前先做一次全局搜索，别用自己拼的路径下结论。**
2. **"embargo_days=0，没有 embargo"** → 错。指标里确实写着 0，但代码路径（`trainer.py:196`）实传 `horizon + settlement`，切分走了 `dataset_manifest.py:317` 的成熟日分组 + 结构性 embargo，实测同一成熟日跨 split = 0，即 embargo 是生效的。真正的问题是**指标记错 + 门禁与切分用了两个不同的日期轴**（L4-a/L4-b）。**教训：指标字段本身也是需要被验证的对象；一个写错的指标比没有指标危害更大，因为它会把人引向错误结论。**
