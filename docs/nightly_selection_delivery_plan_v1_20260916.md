# 晚间选股与飞书交付最小闭环整改方案 v1

日期：2026-09-16。状态：方案，未实施。依据：本地 main@be6453c、同日 NAS 18:56—19:00 取证、用户确认昨晚及白天确实收到消息，以及本轮进一步源码核对。实施前需重新核对 HEAD、生产镜像和工作区差异。

## 1. 修正问题定义

飞书整体可用，用户已确认实际收到消息。不能把“没有独立夜扫报告”说成“晚上没有消息”。

9/15 22:24:57 的《夜间深扫进化完成》由 evolution_core_service._notify_evolution_offhours_completion 发送。消息中的“本轮入围 20 只”取自 week5_refresh.signal_pool.ranking.selected_symbols / selected_count；这是进化复扫短名单。当天 21:45 夜扫的 night_pool 为 1 只、最终信号为 0。三者不相等本身不构成算法错误，但消息未充分区分阶段，无法作为统一交付验收。

本次目标：每个交易日晚间，有且只有一个可追溯的正式选股报告来源；有合格观察候选则列出，没有则说明原因；飞书交付独立可验证、失败可恢复。保留现有白天通知、simulation/advisory_only、交易门禁与默认评分阈值。

## 2. 方案比较与选择

| 方案 | 成本 | 主要缺点 | 结论 |
| --- | --- | --- | --- |
| 仅把夜扫 notify_enabled 改 true | 低 | 内层仍禁止发送；无交付状态和重试；容易误入买入通知链 | 不采用 |
| 统一夜扫报告，复用飞书通道，增加小型持久化待发送记录 | 中 | 需补调度、幂等、失败恢复测试 | 推荐 |
| 改写全部调度、策略、训练和消息系统 | 高 | 范围大、回归面大，仍可能推迟业务验收 | 本轮不做 |

不新增数据库服务、消息队列或第三方依赖。可复用现有文件锁、原子替换、命名卷和调度器；新的职责拆为小服务，不继续把所有逻辑堆入 service.py。

## 3. 统一报告与消息口径

### 3.1 正式结果

只从一次完成的 run_night_scan 返回结果构造正式晚报，保存冻结报告。不能发送时再读取已被盘中雷达或进化复扫改写的通用 latest/watchlist。

报告最小字段：schema_version、report_id、trade_date、generated_at、run_id/trace_id、code_commit、config_hash、data_snapshot_id、scan_status、data_gate、funnel_counts、observation_candidates、final_selection_count、exclusion_summary、fallback_source_date。

- observation_candidates：由当轮 night_pool 生成，正文显示前 5，只剩 1 只就发 1 只。完整池留在报告。
- final_selection_count：保留审计信息；夜间仍不能把它渲染为已满足实时条件的买入指令。
- shortlist：明确称“中间短名单”，不能写成最终入选。
- 旧池：单独列为“上次结果，仅供回顾”，禁止计入今日入选数。
- 缺名称：展示股票代码并注明名称缺失；不得编造或因查询名称失败阻断报告。
- 分数、理由、风险来自同一个冻结报告，禁止通知渲染时重算排序或另跑模型。

### 3.2 四种业务结果

| scan_status | 用户看到的内容 | 系统含义 |
| --- | --- | --- |
| completed | 日期、候选数量、股票/分数/依据/风险 | 本轮正常、有候选 |
| empty | 正常完成、无合格候选、主要过滤原因 | 正常业务结果，不凑数 |
| blocked | 数据日期/覆盖不足等具体原因 | 未完成有效选股，不得称“今日无机会” |
| failed | 超时或异常、失败阶段、后续处理状态 | 技术失败，不得伪装成空候选 |

fallback 是附加信息，不把旧候选包装成新的 completed。

### 3.3 消息示意（沿用已取证历史数据，非新的推荐）

```text
【晚间选股报告】2026-09-15
结果：完成，隔夜观察候选 1 只
数据日期：2026-09-15

1. 001368｜评分 65.89｜观察
   入选依据：使用该报告已有理由
   风险说明：使用该报告已有风险

筛选过程：5486 → 质量池300 → 轻筛100 → 深评50 → 观察1
本报告用于隔夜观察；是否满足盘中买入条件需另行确认。
```

正文不堆放模型发布、manifest、内部模块代号。技术详情放报告/API。

### 3.4 现有消息的兼容

- 白天午盘、收盘消息继续保留。
- 新增独立的正式晚报，不依赖进化任务成功。
- 进化摘要继续可用，但把“候选股票：入围 N 只”改成“进化复扫中间短名单 N 只，非正式晚间观察池”。若需要引用正式结果，引用明确 report_id 的候选数。
- 第一轮不直接关闭进化任务、不撤销其参数控制或观察池写入；先证明正式报告不受后续复扫覆盖。减少消息数量可在闭环稳定后单独配置。

## 4. 可靠交付，不重跑选股来补发消息

### 4.1 状态分开

保留原扫描结果字段兼容旧调用方，增加 scan_status / delivery_status。例如 completed + pending 表示选股完成但未发送，empty + delivered 表示正常空结果已交付。

交付状态：pending、sending、retry_wait、delivered、unknown、exhausted。delivered 仅表示目标飞书 API 明确接受，不表示人已阅读。NAS 验收再结合用户实际收件。

### 4.2 最小持久化

建议目录（新增，置于现有 artifacts 命名卷）：

```text
runtime/nightly_reports/<trade_date>/<report_id>.json
runtime/nightly_delivery/<report_id>.json
```

报告先原子落盘，再创建待发记录。创建第二个文件前崩溃时，轻量恢复任务可从未交付报告补建记录；不得把双文件顺序写入误当成事务。

待发记录保存 report_id、目标标识的非敏感指纹、内容摘要、attempts、next_retry_at、lease_owner/lease_until、last_error、各渠道结果、accepted_at；接口有可用 message_id 时保留。凭据和完整接收人标识不写报告。

复用 DistributedFileLock 实现跨容器排他领取；发送期间不能长持整个候选状态锁。必须验证租约过期与慢请求不会导致两个 worker 同时发送。

### 4.3 幂等与重试

- 同一已冻结 report_id 对同一接收目标重复调度，已成功的不再发送。
- 未成功的重试读取冻结报告，不重新扫描、不重新生成正文时间戳。
- 同交易日内容确有修正，产生新的报告版本，并标“修订版”；不能每次重启产生新 report_id 导致刷屏。
- delivery_id 与扫描运行 ID 分开。修复 `_idempotent_night_scan` 对共享 state.trade_date/data_version 的依赖：使用夜扫自身完成记录和夜扫数据版本，检查完成状态，不能把失败回退或盘中状态当作夜扫完成证据。
- 建议明确失败后的退避为 1、5、15 分钟，总计首次加 3 次重试；失败超过预算进入 exhausted。实现为调度时间，不在 worker 内 sleep。
- 不直接复用 `_notify_if_changed` 当前“先写去重缓存、后发送”的时序；发送失败不得写成已成功去重。
- 超时发生在飞书已接收但本地未记账时，状态应为 unknown。实现前核实当前接口是否支持幂等/状态查询；支持则复用同一键，否则只能提供有界重试和重复风险可观测性，不承诺严格 exactly-once。
- 外部全断网时不可能靠同一飞书通道即时报警；须保留本地失败状态，恢复后补发。

### 4.4 渠道结果

复用现有 feishu_app 和已配置的接收目标，不新建机器人、不改凭据。

当前 factory 使用 RequiredSuccessBroadcastNotifier：主应用为必需目标，企业分发为可选目标。报告必须逐目标保存结果，不能仅凭字符串 feishu_app+feishu_enterprise 推断两路均成功；主目标失败、console 成功不能算交付。

优先提供明确的外部交付接口或兼容性新增字段；若改变通用 FailoverNotifier 的结果结构，需回归全部现有通知调用方。首轮不改变白天消息的旧 success 语义，但正式晚报验收必须用 external_delivered/目标结果。

静默窗口沿用现有 00:30—08:30。到窗口内的未发结果保留 pending，次日窗口结束可作为明确标注日期的补发；不得丢弃或冒充次日选股结果。

## 5. 数据就绪、扫描超时与漏跑

### 5.1 当前预算风险

night_scan_readiness_wait_sec=900；week5 timeout=1800。9/15 完整夜扫耗时约1359秒。因此“等待15分钟 + 类似昨晚的扫描耗时”约2259秒，可能超过30分钟外层限制。这是代码与配置推导的风险，不是已经证明昨晚因此失败。

推荐：数据未就绪时快速返回 waiting 状态，由调度器退避再检查；给真正开始的扫描保留完整执行预算。继续保持21:45作为名义触发时间，首轮不盲目提前，也不把所有 Week5 任务的超时一起调大。

### 5.2 晚间截止与检查任务

建议交付目标22:30、最终截止23:30（新增可配置默认建议，不是现有系统行为）。22:30仍未完成，发送一次延迟说明；23:30仍失败或被阻断，发送一次最终失败摘要，不能整晚沉默。

轻量交付/漏跑检查放在不被 heavy 单槽扫描阻塞的调度路径，例如现有 critical 组新增专用小任务。每次只读取少量记录并处理有限待发条目，设置独立短超时。无需第三个常驻服务。它可识别未启动、运行超时、进程被终止以及报告已保存但消息待发。

延迟/失败提醒与后续正式成功报告使用不同消息类型和幂等键，不能因已发失败提醒而拦住恢复后的结果。

### 5.3 数据身份

保留交易日、coverage、新鲜度门禁，不通过读取昨天数据来凑今日报告。开扫时固定 readiness 证据与数据版本，记录在报告。

源码显示 evolution 成功后可 consume/rename nightly_data_ready.json。消息补发只依赖冻结报告，不再次依赖该文件。必须补“readiness已被其它任务消费”的恢复测试；若新扫描重试确需读取 consumed 凭证，必须核对同一交易日、版本和当前数据状态，禁止无条件把历史 consumed 当就绪。首轮不全局改写 readiness 消费协议。

## 6. PR #82 缺输入边界

保留已修复的统一指标计算，以及原评分/过热阈值。

- 对有效且足量的 OHLC：计算真实 ma5/atr14 后评估。
- 对历史不足、非有限值、无法形成有效ATR等情况：标记 evaluation_status=insufficient_input，指标缺失用 null/缺键表示，禁止退回1.0/0.03假值。
- 维持旧 level 枚举兼容，在外层新增评估状态与原因。正式买入准入显式拒绝“未完成必要风险评估”，原因显示输入不足，而非假称过热。单独检查全部 evaluator 调用方的兼容性。
- 观察报告可以单列“数据待补全”条目，但不能计入通过完整风险检查的候选；不抬分、不凑满5只。
- 同时统计足量输入比例、缺输入数量、真实过热拒绝比例。PR通过后要查看真实夜扫这些指标，不能只检查合成样本。

这属于对缺输入行为的明确收紧；已有默认行为并非注释所说的fail-open。实施时必须把这一变化写入提交说明。

## 8. 分批实施与验收

| 批次 | 内容 | 完成门槛 |
| --- | --- | --- |
| A | 冻结报告、口径统一、消息渲染 | 四类结果正确；进化短名单不冒充正式结果；盘中更新不改变旧报告 |
| B | 外部交付、持久化重试、幂等、重启恢复 | 首次失败后能补发；console不算送达；成功不重复；并发不双发 |
| C | 等待预算、漏跑/超时检查、夜扫幂等修正 | 数据晚到不吞扫描预算；进程被杀有终态；失败不被already_ran吞掉 |
| D | 过热缺输入边界 | 正常不误拒、真过热仍拒、缺输入可解释，生产选择入口验证通过 |
| E | NAS灰度与真实夜间验收 | 同一报告的产物、飞书回执和用户收件一致 |

A—D 可分小提交便于审查，但正式启用晚报必须包含可靠交付能力；不为了凑PR数量拆出无法独立验证的半成品。

最低测试矩阵：有1只/5只、正常0只、readiness缺失/旧日期、门禁失败、旧池回退、运行异常/超时、通知关闭、真实通道失败+console成功、部分目标失败、发送成功去重、失败后重试、API超时不确定状态、进程重启恢复、落盘中途崩溃、双worker争抢、报告修订、quiet window、周末/节假日/跨日、盘中状态覆盖、readiness被consume、过热完整/不足/异常输入。

使用隔离tmp_path与fake notifier；对现有Week5、scheduler、notifier、config相关套件回归，再运行仓库要求的lint/类型/质量检查。生产不安装pytest、不把完整测试集写到实际运行卷。

## 9. NAS上线、验收与回滚

1. 核对发布HEAD、镜像、挂载和现有工作；保留当前镜像与最小配置备份，使用独立晚报开关。
2. 首先以关闭真实发送方式回放已有产物，验证正式报告口径。旧数据显式标日期。
3. 用新交付链向既有目标发送一份明确标注验收用途/历史日期的报告，检查实际收件；不群发新目标。
4. 启用夜间自动链，检查21:45调度、当日数据版本、完成时间、正式报告与飞书目标结果。
5. 一次端到端通过记“功能验收通过”；建议连续3个交易日自动运行通过后记“运行稳定”。0只但合理解释并送达也算业务成功；数据失败有通知只算故障可见，不算选股成功。
6. 验收留存交易日、run_id、report_id、data_snapshot_id、commit、scan_status、delivery_status、渠道回执及用户收件确认；不得仅给health绿色或pytest数量。

回滚优先关闭新增晚报/重试开关、回退对应镜像和配置。保留已发送回执与冻结报告，恢复时不能清空去重记录导致重复发。新增工件与旧版本兼容；本轮不迁移或删除现有数据卷。

## 10. 明确不在本轮承诺内的事项

不保证每天必有合格股票，不以降低阈值作为交付修复；不承诺盈利。盘中雷达超时、竞价基线、模型身份/训练质量作为独立后续任务，只在有证据直接阻断夜间扫描时纳入本轮。

本方案不代表已完成实现或NAS验收。当前已知事实来自本次会话的现场取证；未来部署前需刷新运行证据。
